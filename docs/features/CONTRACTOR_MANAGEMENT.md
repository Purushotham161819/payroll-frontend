# Contractor Management

Contractor Management and its final UI refinements were visually approved on 03 November 2026, independently of Employee Management and Employee Payroll. The Product Owner authorized conservative cleanup, validation and normal publication to main. Historical approval-gate wording in older implementation sections is superseded by this authorization. Phase 4I Dashboard remains deferred.

Use Employees -> Contractors for directory/search, Add Contractor, general Pay Contractors and individual Pay Contractor entry points. First/Last Name opens Contractor Details and Payments. Administrators configure deduction-only components in Settings -> Contractor Settings. Assign deductions in each contractor profile. Both payment entry points share the same form: Payment Date at the top, selected-only Total Gross Payment and Total Net Payment KPIs, checkboxes/select-all, names, manually entered Gross Pay, assigned deduction amounts, Total Deductions and Net Payment. Fixed/percentage rules use Gross Pay; no assigned deductions means Net Payment equals Gross Pay. The inherited restricted Formula option also uses Gross Pay, independently of employee payroll.

Submit opens a confirmation containing the date, contractors, each contractor's Description, Gross Pay, deduction names/amounts and individual/aggregate totals. Description is entered independently in each table row, retained across selection changes and saved in that contractor's immutable entry. There is no common Description input. Older records without an entry Description continue to display their original batch Description. Only explicit Confirm Payments writes records. The backend independently validates and calculates the batch, stores separate immutable contractor entries atomically, and protects retries with an organization-scoped idempotency key. This records payments without transferring money. History never recalculates older entries; missing or null Gross Pay displays Not recorded. All money uses the existing psInr convention, including omitted decimal zeros for nonzero whole rupees and two decimals for zero/fractional values.

The directory displays saved Contractor ID, First Name, Last Name, Email, Contractor Status and a single CDK kebab action menu matching Employee Directory. First Name alone uses the approved semibold weight. The Contractor Status filter uses the existing enhanced native select with All/Active/Inactive; like Employees it defaults to Active, records the filter in the URL and preserves it on Refresh/reload. Search and status filtering work together. Edit reuses the existing contractor form. Authorized admins may confirm permanent deletion of a contractor and its associated payment entries; see the transaction limitation below.

New contractors default to Active without any Status input in Add Contractor. Missing status on legacy contractors is treated as Active without rewriting their records. Admins edit Active/Inactive inside Contractor Details with Save/Cancel and optimistic versions. The profile cards use equal-width/equal-height grid stretching on desktop and stack on smaller screens. Component assignment Edit/Save/Cancel remains intact.

Inactive contractors are excluded from payment eligibility/select-all and stale individual preselection is cleared when fresh data loads. Individual directory menu actions and the Payments-tab Pay Contractor button are disabled with an explanation. The backend also rejects new inactive payments. Previously completed idempotent retries return their saved records rather than creating new payments. History remains accessible while inactive. The Payments-tab button opens the existing shared payment form; it adds no separate calculation or submission path.

View Payment uses labeled contractor identity/date/description fields, compact saved component rows, INR totals and an emphasized Net Payment. Only the top-right accessible cross and Escape close the dialog. The redundant bottom button is removed. Shared close icon controls retain accessible labels without the duplicate visible focus tooltip; other action tooltips and legitimate workflow buttons remain intact.

Permanent deletion requires a transaction-capable MongoDB replica set or sharded deployment. The backend transaction removes the contractor, pulls only its entries from shared payment envelopes and removes only affected envelopes that become empty. Other contractor snapshots remain unchanged. New payment writes acquire a transactional contractor write fence so deletion cannot race with insertion and leave orphan records. Standalone MongoDB rejects deletion with no writes and a clear UI error. The current local deployment is standalone; no database configuration was changed. No soft deletion or unsafe multi-step fallback is used.

The detailed [architecture, API, validation, isolation and limitations guide](https://github.com/Purushotham161819/payroll-backend/blob/main/docs/features/CONTRACTOR_MANAGEMENT.md) is maintained in the backend repository. The [implementation report](CONTRACTOR_MANAGEMENT_IMPLEMENTATION_REPORT.md) contains validation results and the screenshot review gallery.

Presentation reuses existing PageHeader, Card, FormField, Button/IconButton, DataTable, StatusBadge, dropdown, INR/date utilities and the pure API error-message helper. New PsTabs, PsDialog and PsFeatureLayout are generic, opt-in shared controls using existing tokens. No contractor-specific stylesheet or one-off override is introduced.

Routes: /contractors, /contractors/:id and /settings/contractors. The existing employee root route, employee profile/payroll routes and business event handlers remain unchanged. The requested People ribbon and Contractor Settings link are the only existing-page navigation additions. Four browser tests now explicitly target the existing Main navigation Employees link, preserving assertions despite the new ribbon link with the same label.
